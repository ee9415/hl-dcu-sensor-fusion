# 10/15/20 FPS 입력 상한 및 실기 비교 (2026-10-27)

## 변경

- main.py의 카메라·스테레오·인코더 입력 클럭 기본 상한을20FPS로 변경. OAK_INPUT_FPS 환경 변수로10/15/20 중 지정할 수 있다. 이는 실제 인식 출력 FPS 보장이 아니다.
- 장치 TCP8558 응답에 input_fps_limit을 추가하고 PC 송신기가 이 값을 따른다. 이전 장치처럼 값이 없으면 안전하게10FPS로 제한한다.
- 멀티뷰에 PC 전송 FPS10/15/20 선택 메뉴 추가. 구간/반복/진행바 설정과 함께 소스 적용 시 반영한다. 이번 전체 디버깅 구성에서는 높은 입력률이 불리해 UI 기본값은10으로 유지한다.
- 실제 전송 상한=min(설정FPS, 원본FPS, 장치상한). 같은 회차·원본 프레임을 반복 송신하지 않는다. 일시정지 중 탐색은 새 media_epoch의 별도 요청으로 처리하며 기존 동작을 유지한다.
- 상태 문구에 설정/실제 전송 상한/원본/장치FPS를 구분한다. 이 값은 측정된 인식 FPS가 아니다.
- 기존 녹화 형식은10FPS를 유지하되 벽시계 기준으로 리샘플링한다. 입력20FPS를 그대로10FPS 파일에 모두 기록해 재생 시간이 늘어나는 부작용을 방지한다. 영상 녹화에 한해서 프레임 선택/정지 화면 반복이 생기며 NN 입력이나 텔레메트리의 처리량을 부풀리지 않는다. CSV는 실제 수신 결과를 기록한다.
- 경계선 알고리즘, 후보/임계값, 모델, 전처리, 중심선 제외는 그대로다. aab61a8의 정확 중앙값/글리프 캐시를 유지했다.

## 배포 및 시험 조건

OAK4-D Pro 192.168.201.2의 개발 앱에 main.py와 video_transport.py만 교체. 교체 전 백업 /app/deploy_backup_36ac50a9c8. 모델은 기존 person RVC4 파일을 유지했다. 영구 .oakapp 재빌드는 수행하지 않았다.

원본은 사용자 지정 D:/project/halla_yolopv2/KakaoTalk_20261016_170026655.mp4, FPS29.997157/26,378프레임이다. 이전10FPS 녹화파일을 복제해20FPS처럼 세지 않았다.

같은60~76초 구간을20초 동안10→15→20→10FPS로 반복 전송했다. 장치 클럭은 네 번 모두20FPS, RGB/결과/Depth/BEV 생성과 인코딩은 켜진 상태다. 장치 시각 기준으로 발행 처리량과 지연을 계산하고 검증기가 넣는 의도적 정지는 연속 창에서 제외했다. 원본30FPS에서10/15/20Hz로 선택하는 정상 프레임 스킵을 네트워크 누락률로 계산하지 않았다.
