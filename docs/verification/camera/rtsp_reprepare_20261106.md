# RTSP 공유 미디어 재연결 후 지속 수신 검사 (2026-11-06)

## 문제와 재현

0.33.5 배포 후에도 재실행한 멀티뷰에서 인식 결과/TOP 수신이 중단됐다.
처음 제공된 로그에는 영상 연결 요청 없이 상태 확인과 PC 시작 요청만 있었으나,
실제 연결과 PC 전송을 수행한 뒤에도 RGB만 재생되는 별도 문제를 확인했다.
카메라 텔레메트리의 PC/full 추론은 계속 진행되고8553~8556 포트도 열려 있었다.
Windows 독립 수신에서도 인식25프레임 후 정지, TOP0프레임이 발생했으므로
단순 WSL 표시 문제라고 판단하지 않았다.

기존 짧은 재연결 검사와 첫3프레임 검사만으로 지속 수신을 보장할 수 없었다.
verify_starved_reconnect.py는 PC 입력5초 전송 후 중단, 수신 종료, 대기,
입력이 없는 상태의 수신기 선연결, PC 영상 재개를 수행한다.
마지막20초 동안 각 스트림이20프레임 이상 증가하고 최종 연결·프레임 나이3초 미만을
만족해야 통과한다. 앞선 단계 수정본은 이 검사에서 실패했으며 실패 로그를 보존했다.

## 수정 전략

- 공유 팩토리에서도 종료 중인 미디어와 새 미디어가 겹칠 수 있다.
  팩토리 전체에 전송 소스/수요/큐 하나를 두면 새 미디어가 기존 전송을 바꿔 버린다.
- 미디어마다 별도 bounded H264 큐·전송 작업·역압·시간축을 유지하고 모든 활성
  미디어로 동일 인코더 프레임을 배포한다. 한 미디어의 종료는 해당 작업만 닫는다.
- 미디어는 reusable=false로 명시하고 unprepared에서 등록 해제 및 작업 종료를 한다.
- 팩토리는 SPS/PPS만 캐시한다. 새 미디어는 다음 IDR에서 시작하며 큐 초과도
  다음 IDR부터 복구한다. 종료된 미디어 콜백은 새 미디어 상태를 바꾸지 않는다.
- 버퍼 PTS/DTS는 각 미디어의 첫 버퍼0부터 단조 증가하는 명시적 나노초 시간축이다.
  인코더는 기존 B프레임0 설정을 유지한다.
- 입력 수/출력 수/IDR 수/큐/수요/미디어 번호를5초마다 기록해 최초 연결만 성공한
  상태와 지속 전송을 구분한다. 버전0.33.6 준비, 차선 추적 형상 변경은 없다.

## 검증 상태

전송 단위 회귀10개, 전체 회귀374개 통과(57.421초).
동시에 겹치는 미디어의 독립 전달·한쪽 역압·한쪽 종료가 다른 전달을 막지 않는지 검사한다.
입력 단절 후 실제 지속 수신 검사는 artifacts/rtsp_reprepare_20261106에 기록한다.
검증 완료 전 패키지 배포 완료로 판단하지 않는다.

독립 큐 단계 적용본은 강화 재현 검사에 통과했다(`feeds_stage/report.json`).
재개한 PC 영상120~169.9초에서 인식 결과218프레임·TOP219프레임,
최종 프레임 나이 모두0.062초였다. 마지막20초의 프레임 증가 조건도 통과했다.
최초 입력 소실 구간에서는 읽기 시간 초과가 있었고 인식 결과 수신기는1회 재접속했다.
이는 소실 중 항상 연결을 유지했다는 뜻이 아니라 재개 후 지속 수신을 확인한 결과다.

메인 화면에도 기존 연결 동작을 호출하는 '영상 연결' 버튼을 직접 노출했다.
카메라 앱 상태 확인과 영상 수신 연결을 구분해 설정 창을 열지 않고 연결할 수 있다.

## WSL 수신기 추가 원인과 조치

Windows 수신은 지속 수신에 성공한 뒤에도 WSL OpenCV4.5.4는 연결 직후 끊겼다.
별도 OpenCV4.10 수신기의 상세 FFmpeg 로그에서 초기 스트림 분석에10.5286초가
걸린 뒤 정상 연결·30프레임 수신을 확인했다. 기존5초 open timeout은 이보다 짧았다.
기존4.5.4도15초 제한에서는12.9536초에 열리고30프레임 수신했다.
단순 네트워크 장애와 구분하기 위해 WSL에서21,962byte 텔레메트리 수신도 확인했다.

- 수신기 open timeout을15초로 늘리고 read timeout은5초로 유지한다.
  종료 대기도 open 중인 작업을 정리할 수 있도록16초로 맞췄다.
- FFmpeg 초기 FPS 분석량·분석 시간을 제한한다.4.10의 실제 시험은6.0416초에
  연결되고30프레임을10.4913초 안에 수신했다.
- WSL 전용 OpenCV4.10.0.84 wheel을 artifacts/runtime/recorder-wsl-site에 격리했다.
  시스템 OpenCV는 변경하지 않았다. requirements-oak-recorder-wsl.txt로 버전을 고정한다.
- run_oak_recorder.sh는 해당 경로가 있을 때만 PYTHONPATH에 추가하며, 이 런타임에서는
  FFmpeg 병렬 연결과 디코더1스레드를 사용한다. 없으면 기존 Python 환경을 사용한다.
  OPENCV_FFMPEG_IS_THREAD_SAFE/THREADS 지원은 [OpenCV4.10 원문](https://github.com/opencv/opencv/blob/4.10.0/modules/videoio/src/cap_ffmpeg_impl.hpp)에서 확인했다.
- 수신기 버전과 초기 연결 제한을 실행 로그에 기록한다. 녹화 관련 회귀10개 통과.

WSL에 pip가 없어 Windows pip로 Linux wheel을 받아 격리 경로에 풀었다.
재설치 시 pip가 있는 Linux에서는 저장소 루트에서 다음을 사용할 수 있다.
`python3 -m pip install --no-deps --target artifacts/runtime/recorder-wsl-site -r tools/requirements-oak-recorder-wsl.txt`.
현재 WSL NumPy1.21.5와 호환됨을 확인했다. wheel 및 설치·비교 로그는 같은 artifacts에 보존했다.
