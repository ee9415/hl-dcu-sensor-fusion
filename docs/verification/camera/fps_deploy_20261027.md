# nanmedian 정확 대체·글리프 캐시 배포 전후 FPS 비교 (2026-10-27)

## 결론

경계/정지선/렌더 결과가 bit-exact로 같은 두 변경(`nanmedian_columns`, `_draw_text` 글리프 캐시)을 장치에 배포했다. 같은 2~18초 구간 기준으로 발행 FPS가 8.64에서 9.85로 올랐다(실행 평균). 지연도 더 이상 누적되지 않았다. 롤백 후 재측정에서 이전 값이, 재배포 후 재측정에서 개선 값이 다시 나왔으므로(A-B-A-B) 재시작이나 측정 순서 효과가 아니다. 다만 실행 중 HEALTH 단일 프레임 후처리 시간이 약 81~110ms로, 100ms 입력 주기에 붙어 있어 여유가 작다. 20초 창보다 긴 지속 운행은 검증하지 않았다.

## 조건

- OAK4-D Pro 192.168.201.2, person RVC4 모델. 모델·전처리·임계값·후보 수는 변경 없음.
- 입력: `20261026_174939_70502991` RGB 녹화, 2~18초를 20초 동안 반복 송신(목표 10Hz). 검증기가 넣는 일시정지/재개 구간은 계산에서 제외(검증기와 같은 연속 창).
- before: 장치 기존 코드(HEAD 내용, CRLF). after: 작업 트리의 `image_boundaries.py`, `yolopv2_node.py`.
- 동등성: `boundary_replay_runner.py`/`replay_boundary_equivalence.py`. 장치 numpy 2.5.4에서 실제 캡처 173프레임 + 합성 160 + fixture 40프레임이 바이트 단위로 동일.
- 지표 계산: `src/hl_camera_bringup/scripts/compare_pc_replay_runs.py`. P95 규칙은 `analyze_oak_profile.py`와 같다.
  - 고유 입력 소비율 = 창 안의 고유 (media_epoch, frame_index) 수 / 창이 걸친 원본 프레임 수.
  - 누락률 = 1 − 소비율. 송신기·1프레임 hub·카메라 tick 중 어디서 누락됐는지는 텔레메트리만으로 구분할 수 없다.

## 측정 도구 변경

- `verify_pc_video_device.py`: 텔레메트리 수신 소켓의 유휴 타임아웃을 2초에서 10초로 늘렸다.
  - 처리량이 개선되어 backlog가 없어지자, 의도된 약 2초 일시정지 동안 텔레메트리가 끊겼다. 그 결과 수신 스레드가 timeout으로 종료되고 검증이 실패했다.
  - 판정 기준과 FPS 계산은 그대로다. rollback_before 두 실행이 바뀐 검증기로 측정한 before 값이다.
- `deploy_app_files.py`: 백업(SHA-256 기록) → 분할 업로드 → 장치에서 compile·해시 확인 → 교체 → backend 재시작. `rollback --backup <dir>`로 원복한다.
