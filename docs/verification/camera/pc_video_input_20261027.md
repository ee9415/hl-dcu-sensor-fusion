# PC 영상 입력 및 장치 인식 검증 (2026-10-27)

## 목적과 구성

모니터를 카메라로 촬영하는 대신 PC의 영상 파일을 OAK4-D Pro로 보내 기존 YOLOPv2 파이프라인에서 처리한다. 멀티뷰에 카메라/PC 영상 파일 선택, 파일 선택, 반복 재생, 적용/전송 시작, 일시정지/재생, 전송 중지 메뉴를 추가했다.

경로는 `VideoFileSender → TCP 8558 → VideoInputServer → VideoInputSelector → 기존 전처리/NN/후처리 → RTSP 및 TCP 텔레메트리`다. PC에서는 파일 디코딩과 JPEG 전송만 수행한다. 추론은 장치에서 실행한다. RGB 출력도 선택한 소스를 사용한다. 기존 RTSP 포트(8553~8556)와 텔레메트리 8557은 유지한다.

## 사용 방법

1. 변경된 멀티뷰 앱을 재실행하고 장치 IP로 영상 연결한다.
2. 영상 소스에서 **PC 영상 파일**을 선택하고 **영상 파일 선택**으로 파일을 지정한다.
3. 반복 여부를 선택한 뒤 **소스 적용 / 전송 시작**을 누른다.
4. 일시정지/재생 또는 전송 중지 버튼으로 송신을 제어한다.
5. 실제 카메라로 돌아가려면 **카메라**를 선택하고 소스 적용 버튼을 누른다.

영상 파일 선택만으로 전송하지 않는다. 녹화 중에는 소스 변경을 막는다. 영상 연결/소스 선택은 CSV 저장을 시작하지 않으며 기존 녹화 시작/중지와 로그 저장 연동을 유지한다. CSV 프레임에는 입력 종류, 파일명, 원본 프레임 번호, 파일 내 시각, 재생 회차, 소스 세대 및 Depth 유효 여부를 추가한다.

### 진행바 및 탐색 추가 (2026-10-27)

PC 전송 위치 슬라이더에 현재 시각/구간 종료 시각, 진행률, 반복 회차를 표시한다. 시작1:00/종료2:00이면 1:00이0%, 1:30이50%이며 반복 후1:00/0%로 돌아간다. 소스 적용한 구간을 기준으로 계산하므로 아직 적용하지 않은 입력란 편집과 섞이지 않는다. 종료 공란도 확인된 파일 길이를 사용한다. 단회 완료는100%, 정지·일시정지는 마지막 위치, 카메라 복귀는 대기로 표시한다. 위치는 PC 송신 기준이며 실제 NN/RTSP 화면 재생 위치와는 지연이 있을 수 있다.

드래그 또는 방향키로 구간 안의 재생 위치를 이동할 수 있다. 디코더 소유 스레드가 요청을 처리하며 마지막 프레임 안으로 제한한다. 일시정지 중 탐색은 해당 프레임 하나를 전송한 뒤 정지를 유지한다. 탐색도 media_epoch를 변경해 기존 장치 추적 이력을 초기화한다. 사용자 표시 반복 회차(loop_count)는 탐색과 분리해 실제 반복 때만 증가한다. 재생 완료/전송 중지 상태에서는 소스를 다시 적용해야 탐색할 수 있다.

실제 파일·TCP 검사에서 정지 중1.4초 탐색, 하단/상단 범위 제한, epoch 변경, 회차 유지, 정지 유지 및 재개를 확인했다. 실제 Tk UI에서는 진행률60% 이후 반복 때0% 복귀, 정지 중90% 탐색, 단회 완료100% 표시를 확인했다. 전체116개 회귀 검사 통과. 근거는 artifacts/pc_video_input_20261027/gui_check.json. 장치 수신 코드 변경은 없다.

### 구간 설정과 검증

전송 구간 시작·종료 입력란을 추가했다. 초, 분:초, 시:분:초 형식을 지원한다. 시작62/종료84 또는 시작1:02/종료1:24로 같은 구간을 선택할 수 있다. 종료 공란은 영상 끝이며 반복 체크를 해제하면 구간을 한 번만 보낸다. 구간 변경은 소스 적용 시 반영한다.

범위는 시작 포함·종료 제외다. 원본 FPS 기준 해당 시각 이상의 첫 프레임부터 종료 시각 미만 프레임만 최대10Hz로 전송한다. 파일 FPS/길이와 탐색 결과를 검증한다. 음수·무한대·역전 구간·영상 길이 초과·프레임 없는 구간은 전송하지 않는다. 재생 시각과 CSV 프레임 번호는 원본 파일 기준을 유지하며 반복 회차를 별도 표시한다. 구간 반복마다 기존 소스 세대 변경으로 장치 추적 이력이 초기화된다.

실제 AVI/JPEG 픽셀 및 TCP 검사에서 0.55~1.05초 범위의 프레임6~10만 전송했고 단회/반복 모두 통과했다. 실제 Tk 시작·종료 입력란으로 0.5~0.9초 구간 반복·일시정지·재개·카메라 복귀를 확인했다. CSV 자동 시작 없음 및 입력 컨트롤 배치 검사도 통과했다.

전체114개 회귀 검사 통과. 실제 OAK에 2~3초 구간을 반복 송신한 최종 검사에서 반환58프레임의 구간 밖 시각0, 회차0~6, 출력9.74 FPS, 입력 시퀀스 불일치0, 유효 Depth 객체0, 중심선0, 일시정지/재개 및 카메라 복귀 통과. 근거는 artifacts/pc_video_input_20261027/range_device_final/report.json 및 frames.jsonl. 초기 검사는 전환 전 기존 다른 파일의 지연12프레임까지 집계해 실패했다. 검증기를 카메라3프레임 확인 이후 새 재생만 집계하도록 수정하고 재검증했다. 구간 추가는 PC 송신/UI 변경으로 기존 장치 수신 프로토콜을 그대로 사용한다.

## 동작 범위와 부작용 방지

- 송신은 최대 10 FPS, 960×540 JPEG(품질85)이며 종횡비를 유지하고 여백을 추가한다. 고FPS 파일은 재생 시간에 맞춰 프레임을 건너뛴다. 장치에서는 1920×1080 NV12로 기존 경로에 투입한다.
- 한 연결만 PC 발행자가 될 수 있다. 수신 대기는 최신 1프레임으로 제한한다. JSON 헤더 4096바이트, 페이로드 2MiB, JPEG 최대1920×1080 제한을 적용한다.
- 일시정지, 파일 종료, 연결 끊김 때 임의로 카메라로 전환하지 않는다. 마지막 화면이 남을 수 있으며 상태 문구로 전송 상태를 확인해야 한다. 다시 적용하면 새 연결을 시작한다.
- 소스 전환/파일 반복 시 경계 및 정지선 추적 이력을 초기화해 서로 다른 입력의 상태가 섞이지 않도록 한다. 프레임 번호별 출처를 NN 출력과 연결하며 매칭되지 않는 결과는 버린다.
- PC 영상은 실제 스테레오 Depth와 대응하지 않는다. Depth를 0으로 대체하고 객체 거리를 무효 처리한다. UI에도 Depth/거리 없음으로 표시한다. BEV는 기존 미보정 참고 투영이다.
- 카메라 모드는 원본 RGB/정렬 Depth를 그대로 전달한다. PC 모드도 장치 카메라의 10Hz 시각을 사용하므로 카메라/스테레오 파이프라인은 계속 필요하다.
- TCP8558은 기존 개발용 스트림과 같은 신뢰 가능한 장치 LAN용이며 인증/암호화된 인터넷 입력 서비스가 아니다.
- RTSP 수신은 TCP와 열기/읽기 5초 제한을 적용해 수신 장애 시 재시도한다.

## 배포와 복구

현재 실행 중인 개발 컨테이너에 main.py, yolopv2_node.py, video_transport.py, video_input_node.py를 배포하고 해시/문법 검사 후 backend를 재시작했다. 장치에 opencv-python-headless 4.10.0.84를 설치했으며 requirements에도 반영했다. 모델 파일은 교체하지 않았다.

원본은 `/app/video_input_backup_628d5fc645`에 보존했다. 배포 파일별 SHA256은 `artifacts/pc_video_input_20261027/deploy_v2/deployment.json`에 기록했다. 개발 컨테이너 수정이므로 이미지를 새로 설치하면 사라진다. 영구 재설치에는 변경된 앱 소스로 이미지를 다시 빌드해야 한다.

첫 장치 실행에서 HostNode의 읽기 전용 out 속성과 충돌한 출력을 video_out/depth_out으로 수정했다. RAW16 setFrame은 크기를 설정하지 않으므로 width/height를 명시했다. 두 항목은 실제 DepthAI 환경에서 확인했다.

검증 도구는 src/hl_camera_bringup/scripts/의 check_video_source_gui.py, verify_pc_video_device.py, preview_pc_video_multiview.py, deploy_video_input.py다. ROS2 인터페이스 변경이 없는 standalone 앱/PC 도구 변경이므로 colcon/ROS2 launch 검사는 해당하지 않는다.
