# 클로드 검토 우선순위에 따른 녹화 보강 (2026-11-03)

## 변경 및 정책

### 상태 통신

- 카메라 입력을 처음 확인하는 단계는 기존처럼 성공해야 녹화를 시작한다.
- 녹화 중 timeout/OSError/일시 EOF는 경고 후 재시도한다. 기본1초 간격,
  연속3회 실패 또는 확인 불확실8초 초과 시 종료한다. 시간은 요청 시작 시점부터 센다.
- 명시적 ok:false, 카메라가 아닌 입력, source_epoch/reconnects 변경은 즉시 종료한다.
  프레임 수신 끊김/신선도3초 제한과 그룹 전체 오류 정지 정책도 유지한다.
- 재시도 중 source_verified=false와 경고/복구 이벤트, 확인 불확실 구간 시작 시각 및
  누적 시간을 기록한다. 영상이 계속 수신돼도 이 구간은 카메라 소스 확인이 불확실하다.
  외부 프로그램이 입력을 바꾸는 경우를 재시도만으로 완전히 막을 수는 없다.
- 실제 녹화 일정이1초 넘게 밀리는 경우의 중단 기준은 변경하지 않았다.
  0.25초 이상 지연은 단계별 시간과 함께 경고를 남긴다. 밀린 영상을 조용히 건너뛰지 않는다.

### 오류/저장

- error/error_kind는 최초 오류를 보존한다. release/이벤트 로그/세션 정보 등
  후속 오류는 finalize_errors에 추가한다. OAK-D의 호스트 오류와 worker stderr도 분리한다.
- 녹화 시작 여유 공간256MiB, 진행 중64MiB 미만에서 거부/정지한다.
  이는 전체 녹화 용량 예약이나 녹화 가능 시간 보증은 아니다.
- 기본5초마다 파일 크기와 여유 공간을 확인한다.64KiB 이상 출력이 확인된 뒤
  30초 동안 증가하지 않으면 중단한다. 초기 저비트레이트/FFmpeg 버퍼링은300초 유예한다.
  크기 증가는 디스크에 모든 데이터가 영구 저장됐다는 보증이 아닌 진행 상태 검사다.
- 녹화 설정에 기본 on인 `종료 후 MP4 프레임 수·첫/마지막 프레임 검증`을 추가했다.
  종료 후 프레임 수가 요청 수와 같고 첫/마지막 프레임이 읽혀야 verification=passed.
  검증 off는 skipped, 선행 오류는 skipped_due_error로 기록한다. 전체 프레임 무결성이나
  전원 장애 복구를 검증하는 기능은 아니다.
- writer를 먼저 해제한 뒤 상태 모니터를 기다린다. session.json과 그룹 JSON은
  임시 파일 작성 후 교체한다. 시작 중 실패한 그룹도 UI가 참조를 유지한다.

### CAM01 공유 수신기

- 프레임 잠금과 writer 잠금을 분리했다. 프레임 참조 교체만 프레임 잠금 안에서 하고,
  스냅샷 복사와 기존 인식 탭의 MP4 쓰기는 밖에서 실행한다.
- RTSP 재연결 횟수를 기록하고 짧은 재연결도 그룹 녹화의 소스 변경으로 감지한다.
- 기존 writer가 느려도 스냅샷 잠금을 오래 보유하지 않는다. 다만 기존 writer는
  수신 스레드에서 실행하므로 매우 느린 저장이 수신 자체를 지연시키는 가능성은 남는다.
  인식·검증 탭의 녹화, CSV, 두 탭의 독립 정지는 유지한다.

## 검증

- 최종 전체224개 검사와 기존 Tk 제어 검사 통과.
- 실제 로컬 TCP 프로토콜로1회 timeout/EOF 후 회복 시 녹화 유지,
  연속3회 실패 종료, 불확실 시간 한도 초과, epoch 변경/ok:false 즉시 종료 확인.
- 수신 끊김 뒤 release와 metadata 저장이 함께 실패해도 최초 오류 보존 확인.
- 여유 공간 부족 시작 거부, 데이터를 쓰지 않는 writer의 파일 증가 정지 감지,
  실제 MP4 종료 검증 및 writer 선해제 확인.
- 실제 CaptureSource._capture_loop에서 느린 따라잡기 writer가 실행되는 동안
  record_snapshot이50ms 미만으로 반환되는 검사와 짧은 RTSP 재연결 감지 검사 통과.
- 재연결 테스트의 유한 Mock 목록을 제거하고 source_changed를 명시적으로 검사한다.
  비교 코드를 삭제한 변형을 실행하자 검사1개가 실패함을 확인했다. 기존처럼 다른 예외로
  성공하는 문제가 아님을 검증했다. 근거 mutation_report.json.
- 가상 통합120초: CAM01은 생산 CaptureSource/FFmpeg에 로컬 MJPEG를 공급하고,
  실제 TCP 상태 확인 경로에서1회 timeout을 주입했다. CAM02~06은 가상 worker.
  숨긴 Tk 창에서 실제 ImageTk 렌더링을 실행했다. 기존 writer와6대 녹화를 동시에
  실행하여 MP4총7개를 첫/마지막 프레임까지 읽었다. 새 탭 정지 뒤 기존 writer 지속 확인.
  CAM01/기존 writer1920×1080,2~6번1280×720, 저장10FPS. 그룹6개는각1200~1201프레임.
- 기존 탭/소스 적용·전송/점수 표시·실패 복원 UI 검사는 유지된다.

근거: artifacts/recorder_hardening_20261103/virtual_ui_report.json,
virtual_sessions/*/recording_group.json, mutation_report.json 및 해당 회귀 검사.

카메라/외부 네트워크에 접속하거나 앱·모델을 배포하지 않았다. 실장치 H.264 RTSP,
실제 도로의 비트레이트, Windows 네이티브 녹화, PoE 장애, 장시간 부하 검증은 아니다.
가상 통합은 WSL/Python3.10/OpenCV4.5.4, 로컬 MJPEG였으며 실제 카메라 경로와 다르다.

## 백업과 롤백

본 수정 직전8개 기존 파일을 바이트 단위로 복사하고 SHA256을 기록했다.
백업: artifacts/recorder_hardening_20261103/backup/manifest.json.
수정 후 체크섬도 기록하여 이후 변경이 있으면 덮어쓰기를 거부한다.
문서/검증 산출물은 남으며, 아래 복원은 본 수정에 포함된 기존8개 파일만 되돌린다.
실행 중인 멀티뷰를 종료한 뒤 프로젝트 폴더에서:

```powershell
python artifacts/recorder_hardening_20261103/rollback.py
python artifacts/recorder_hardening_20261103/rollback.py --restore
```

첫 명령은 확인만 한다. 이후 다른 수정이 있으면 자동 복원하지 말고 파일 차이를 확인한다.
실제 작업 폴더를 되돌리지 않고 임시 복사본에서 복원 및 덮어쓰기 방지 검사를 수행한다:

```powershell
python artifacts/recorder_hardening_20261103/rollback.py --self-test
```

위 self-test에서8개 파일 원본 체크섬 복원과 이후 변경 덮어쓰기 거부를 확인했다.
실제 작업 폴더는 되돌리지 않았다.

호스트 UI/녹화 코드 수정이므로 멀티뷰 재시작 후 적용된다.

## 추가 검토 반영: 종료 이벤트 및 손상된 상태 응답

- 종료 처리에서 모니터 종료를 기다린 뒤 상태 이벤트 큐를 다시 비우고 `finish`를 기록한다.
  녹화를 중단시킨 `source_status_failed` 이벤트가 JSONL에서 빠지는 경합을 방지한다.
- 상태 응답 헤더/JSON 손상으로 발생한 ValueError는 ConnectionError로 취급해 기존 일시 통신 오류 정책으로 재시도한다.
  명시적 `ok:false` 또는 카메라 입력 변경은 기존처럼 즉시 종료한다. 최초 오류와 추가 정리 오류는 분리한다.
- 일시 손상 1회 회복, 연속 손상/timeout 종료 및 실패 이벤트 기록 검사를 포함한다.
  원본은 `artifacts/recorder_hardening_20261103/claude_before_p2fix`에 보관했다.
  이후 설정/UI 변경이 더해졌으므로 이전 롤백 체크섬을 임의로 갱신하거나 강제로 우회하지 않는다.
