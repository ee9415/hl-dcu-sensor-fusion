## 요청과 대상

사용자 첨부 RGB/TOP 화면에서 분홍 추적선이 도로 표식과 크게 어긋나는 현상을 검증했다. 원본은 artifacts/recordings/six_camera/six_camera_20261104_073117_05e93c/cam01/cam_01_rgb_20261104_073117.mp4, 10FPS·9845프레임·984.5초로 UI의 16:24.5와 일치한다. 59.7초 프레임을 추출했다.

## PC 재추론

- 기존 사용자 모델의 320×320 ONNX FP32로 0~63초 631프레임을 처리했다. RGB/255·검은 letterbox·0.5 인지 임계값·현재 contour 추적기를 사용했다. 카메라 FP16/JPEG 전송 경로와 동일한 결과라고 주장하지 않는다.
- 동일 마스크에 대해 추적 시작점을 0초·50초·58초로 비교했다. 반응 속도 1.0배와 실제 장치에서 읽은 3.0배를 각각 검증했다. 장치 속도·표시 설정은 변경하지 않았다.
- 59.7초에는 양쪽 모두 observed, 차선 마스크 2602픽셀이었다. 6개 조합 모두 사진과 같은 큰 유지선 이탈은 재현되지 않았다.
- 3.0배에서 0초 시작 대비 다른 시작 이력의 최대 수평 차이는 왼쪽 3.62px, 오른쪽 2.70px(320×180 좌표)였다. 정답 대비 오차가 아니라 추적 시작점 간 차이다.
- 마스크는 오른쪽 흰 표식 외에 왼쪽 노란 표식·도로 연석·우측 외곽도 검출한다. 따라서 마스크 존재와 자차 경계 선택의 정확성은 구분해야 한다. 원거리 및 표식 간 공백은 표시선의 유지/연장 부분을 포함한다.

첨부 사진의 큰 이탈을 정상 동작으로 판정할 수 없다. PC에서는 마스크와 관측 추적선이 생성되지만, 실제 장치의 동일 프레임 상태는 수집되지 않아 FP16 출력·전송 전처리·실제 과거 추적 이력 중 어느 것이 원인인지 확정하지 않는다. 다음 실장치 검증은 기존 PC 전송 점유를 정상 종료한 뒤 55~63초를 재생하며 source_media_time_s와 맞춘 마스크/추적 텔레메트리를 수집해야 한다. 정상 관측 마스크가 있는데도 유지 상태인지, 후보 배정/재검출 확인에서 탈락했는지 확인한 뒤 수정 범위를 결정한다.

패키지/앱 코드 배포·카메라 재시작·인지 임계값·속도 변경은 수행하지 않았다.

## 실장치 재검증 및 원인 확인 (2026-11-10 후속)

### 확인된 원인 1: 마스크가 있어도 왼쪽 후보 전체가 탈락

실제 카메라의59.6초·59.7초·60.0초 마스크는 각각2681·2677·2705 양성 픽셀이며, 왼쪽 노란 표식과 연석 쪽 근거가 존재한다. 그러므로 단순히 모델이 아무 차선도 검출하지 못하는 문제는 아니다. 모델은 연석과 외곽도 차선으로 검출하므로 의미적 선택 혼동은 남아 있다.

ImageBoundaryTracker.update_contours는 측정 스켈레톤을48개 행에 표본화한 후 _smooth_shape 검사로 후보 전체를 판정한다. 최대 절대 기울기4 및 인접 기울기 변화1.8을 요구한다. 실제 왼쪽 곡선은 노란 표식/연석 연결 부근의 작은 국소 꺾임 때문에 다음과 같이 탈락한다(320×180 좌표).

### 확인된 원인 2: 유지·반대편 변화 전달·재검출 지연이 누적

후보가 탈락하면 이전 스켈레톤을 유지하면서 관측되는 반대편 선 변화량의2차식 보정을 전달한다. 전달 목표는 관측된 신뢰 구간에서 적합한 뒤 기존 유지선 영역으로 평가한다. 따라서 이전 형상이 틀어진 상태에서는 유지선이 현재 마스크 위치와 달라질 수 있다. 속도 제한은 이동량 제한이며 정답 위치 보장이 아니다.

0초부터 연속 재생한 실장치 실행에서 오른쪽은57.0초 시점 약10.00초 동안 직접 관측 갱신이 없는 inferred 상태였고, 새 관측과 이전 선 차이가69.32px였다.57.2초 재검출 확인 시80.02px 차이에서 확정됐다. 이 값은320×180 영상 좌표의 이전 선 대비 관측 차이90백분위이며, 정답 레이블 대비 오차가 아니다.57.6·58.3초에는 held/held,58.1초에는 aligning/inferred가 나타났다.58.1초 오른쪽의 반대편 보정 이동은24.001px/해당 프레임이었다(3배 속도120px/s·약0.2초 제한 이내).

즉 마스크 존재에도 후보 탈락/재검출 확인 때문에 오래된 선을 표시하는 경로를 실장치에서 확인했다. 사진과 동일한 모든 픽셀의 재현을 주장하지 않지만, 근접 구간의 장기 유지·큰 관측 불일치·유지/보정 상태를 수치로 확인했다.

### 59.7초 정확 프레임

진단 실행에서59.7초 왼쪽은 aligning, 오른쪽 observed였다. 왼쪽 재검출 직전 prior_error_px15.712, 표시 잔차4.569px; 오른쪽 표시 잔차0.696px였다.59.6초 후보 탈락 후59.7초 후보가 복귀해도 현재 표시가 즉시 관측선으로 붙지 않는 과정이다. 원본 시작 이력·실제 처리 프레임 간격에 따라 세부 상태가 달라지므로 UI 전송 위치 숫자만으로 모든 출력 영상의 정확한 프레임 상태를 판정하지 않는다.

### 개선 대상과 복구

개선 대상은 모델 재포팅이나 선 굵기가 아니라 후보 검증·유지선 보정·재검출 처리다. 국소 꺾임 때문에 전체 차선을 제거하지 않도록 유효 구간 단위 검증을 검토하고, 반대편 보정의 관측 밖 변형을 제한하며, 실제 마스크 근거가 돌아올 때 재결합을 검증해야 한다. 임계값만 크게 풀면 오검출 부작용이 있어 별도 회귀가 필요하다. 이번 요청에서는 원인 검증만 하고 해당 알고리즘 수정은 하지 않았다.

진단 후 기존 code3 release dc27d8b55acae22d4aa39eebc044547f72c802d06de47844db17629e92a410cb으로 복구했다. 이전 정상 복구 대상도 원래 code2(299a76...)로 복구했고 pending/last_failure 없음, runtime fingerprint 유지 확인. 임시 진단 코드와 캡처 파일은 근거로 보관하지만 활성/이전 정상 대상으로 남기지 않았다. 전체 패키지 재설치 없음. 검증 전송 종료 후 camera 소스로 복귀해 빈 PC 입력 점유를 해제했다.

### 최종 UI 복구 확인

기존 멀티뷰 RGB 수신이 멈춰 있어 녹화·미저장 파일 비활성을 확인한 뒤 이전 인스턴스를 종료하고 tools/run_oak_recorder.sh로 새 인스턴스를 실행했다. 정상 종료 요청에 응답하지 않는 이전 PID317은 명령줄을 확인한 뒤 SIGTERM으로 종료했고 새 PID2031 하나만 남겼다. PC 전송은 시작하지 않았고 녹화도 시작하지 않았다. 기존 UI의 59.7초 전송 위치 숫자는 새 미리보기 프레임 시각으로 사용하지 않는다.
