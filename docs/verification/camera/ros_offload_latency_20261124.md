# PC 영상 전송→OAK 추론→ROS 후처리 결과 발행 지연

2026-11-24, CAM01 169.254.100.228, 기존 0.33.10 실행 환경과
e9f2f1d52d6ed026ba238ea9ca6bf52a9c154d79f3ea88de38461adb89fd7396 코드 유지.
ROS 수신/후처리 노드에 가벼운 시간 진단 필드를 추가하고 재시작했다.
카메라 코드는 재배포하지 않았다.

## 방법

- 사용자 제공 cam_01_rgb_20261104_073117.mp4의 처음30초를10FPS로 전송.
- 카메라 원본 묶음 전송 상한은 기존5FPS 유지.
- 원본 영상 frame_index로 PC 송신과 결과를 대응했다. 모든 경계 측정은
  같은 WSL 호스트의 monotonic clock이므로 카메라 wall clock 오차를 사용하지 않는다.
- 시작점: PC가 JPEG 프레임에 대해 send_message를 호출하기 직전.
- 끝점: 후처리 결과 `/oak/postprocess/result`의 publish 호출이 반환한 직후.
  ROS middleware에 발행 요청을 넘긴 시점이며 모든 구독자의 수신 완료 시점은 아니다.
- 별도 timing 토픽에 결과 발행 후의 시간을 기록해 수신했다.
- 117개 표본 중 소스 전환 직후3초를 제외한106개를 정상 상태 집계로 사용.
- 추가 검증 영상 기록기·대용량 원본 모니터 구독 없이 두 ROS 노드와 시간 진단 구독만 실행.
- 파일 디코딩/프레임 선택 대기, 화면 표시 지연은 기본 지연에 포함하지 않는다.

첫3초를 포함한117개 전체 평균693.67ms, P95 838.48ms, 최대941.47ms.
카메라 내부의 NN 추론만을 따로 분리한 시간은 이번 측정에 없다.
영상 출발 후 결과까지 약0.69초의 지연이며, 출력 간격 약0.26초와 다른 지표다.

가장 큰 측정 구간은 호스트의 원본 묶음→ROS 후처리 콜백 전달이다.
이 안의 메시지 생성·직렬화·DDS 전송·executor 대기 각각의 기여는 추가 계측이 필요하다.
이 수치만으로 네트워크나 NN 추론이 단일 병목이라고 결론내릴 수 없다.

## 카메라 10FPS 추론 완료 별도 확인

같은 영상20초·10FPS 입력에서 source_frame_index 0~199의200개가 모두 NN 뒤
마스크/NMS 처리를 완료하고 telemetry에 기록됐다. 입력 누락0, RGB/NN sequence
불일치0. 카메라 입력 수신/소비 카운터만을 추론 완료로 간주한 시험이 아니다.
호스트의 완료 알림 수신 시각 기준199개 간격/19.7583초 =10.0717FPS,
평균 간격99.29ms, P95간격153.72ms, 최대186.08ms였다.
따라서 이20초 조건에서는10FPS 입력을 모두 추론했으며 매100ms 정확히 균등한
완료 간격까지 보장하는 것은 아니다. ROS 대용량 결과 전송 상한5FPS는 그대로다.

PC 입력은 당시 라이브 카메라 프레임의 timestamp를 재사용한다. 그 timestamp
범위로 계산한9.34FPS는 호스트 실제 완료 수신 구간10.07FPS와 다르므로
PC 영상의 처리량 판정에 사용하지 않았다. 끝단 시간은 동일 호스트 monotonic
시계로 측정한다. 자료 artifacts/ros_offload/inference_10fps_20261124/report.json,
frames.json, 도구 tools/measure_oak_inference.py. 종료 후 라이브 카메라 입력 복구.
